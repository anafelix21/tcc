4. Paso a Paso Detallado

Paso 1: Crear Amazon RDS SQL Server (Toma 10-15 min)

¡Hacer Primero! La base de datos tarda ~12 minutos en aprovisionarse. Lánzala mientras configuras los Security Groups e instancias EC2.
  1. En AWS Console en español → escribe RDS → Bases de datos → Crear base de datos.
  2. Método: Creación estándar | Motor: Microsoft SQL Server | Edición: SQL Server Express Edition.
  3. Identificador de instancia: agropacayales-rds-sqlserver
  4. Usuario maestro: admin | Contraseña maestra: AgroPacayales2026!
  5. Clase de instancia: Clases ampliables → db.t3.micro (1 vCPU, 1 GiB RAM).
  6. Almacenamiento: gp3, 20 GiB. Desmarcar "Habilitar escalado automático de almacenamiento".
  7. Conectividad: VPC predeterminada | Acceso público: No | Grupo de seguridad: Crear nuevo llamado evi-rds-sg.
  8. Desmarcar copias de seguridad automáticas y clic en Crear base de datos.
  9. Una vez en estado Disponible, copia el Punto de enlace (Endpoint).

Paso 2: Configurar Grupos de Seguridad (Security Groups)

En el buscador de AWS escribe EC2 → en el menú izquierdo entra a Grupos de seguridad:

  • evi-ec2-sg (Para las 5 máquinas EC2):
    • SSH (TCP 22): 0.0.0.0/0
    • TCP personalizado (30000 - 30002): 0.0.0.0/0 (Frontend, Swagger y Flask)
    • TCP personalizado (6443): Origen evi-ec2-sg (API K3s)
    • TCP personalizado (10250): Origen evi-ec2-sg (Kubelet)
    • UDP personalizado (8472): Origen evi-ec2-sg (Red Flannel)
    • TCP personalizado (27017): Origen evi-ec2-sg (MongoDB)
  • evi-rds-sg (Asignado a RDS SQL Server):
    • MSSQL (TCP 1433): Origen evi-ec2-sg (Solo las EC2 de la VPC pueden entrar)

Paso 3: Lanzar las 5 Instancias EC2 con User Data

Lanza 5 instancias con AMI Ubuntu 24.04 LTS (x86_64), par de claves .pem, IP pública habilitada y grupo evi-ec2-sg:

1. ec2-mongodb (t3.small): En 'Detalles avanzados' → 'Datos de usuario' pega:

#!/bin/bash
set -e
apt-get update && apt-get install -y gnupg curl
curl -fsSL https://www.mongodb.org/static/pgp/server-8.0.asc | gpg --dearmor -o /usr/share/keyrings/mongodb-server-8.0.gpg
echo "deb [ signed-by=/usr/share/keyrings/mongodb-server-8.0.gpg ] https://repo.mongodb.org/apt/ubuntu noble/mongodb-org/8.0 multiverse" | tee /etc/apt/sources.list.d/mongodb-org-8.0.list
apt-get update && apt-get install -y mongodb-org

# Parche rseq para Ubuntu 24.04
mkdir -p /etc/systemd/system/mongod.service.d
printf '[Service]
Environment="GLIBC_TUNABLES=glibc.pthread.rseq=1"
' > /etc/systemd/system/mongod.service.d/rseq.conf
systemctl daemon-reload

sed -i 's/bindIp: 127.0.0.1/bindIp: 0.0.0.0/' /etc/mongod.conf
systemctl enable --now mongod
sleep 6

mongosh --eval 'db.getSiblingDB("admin").createUser({user:"admin",pwd:"Mongo12345",roles:["root"]})'
printf "
security:
  authorization: enabled
" >> /etc/mongod.conf
systemctl restart mongod
apt-mark hold linux-aws linux-image-aws linux-headers-aws

2. k8s-master (t3.small): En 'Datos de usuario' pega:

#!/bin/bash

Paso 4: Unir Workers a K3s y Etiquetar Nodos

1. Conéctate por SSH a cada uno de los 3 workers y ejecuta:

curl -sfL https://get.k3s.io | K3S_URL=https://<IP_PRIVADA_MASTER>:6443 K3S_TOKEN="agropacayales-token-2026" sh -

2. Conéctate por SSH a k8s-master y etiqueta cada nodo:

# Ver nodos conectados
kubectl get nodes

# Etiquetar cada worker con su rol de cómputo
kubectl label node <NOMBRE_NODO_FRONTEND> role=frontend
kubectl label node <NOMBRE_NODO_BACKEND> role=backend1
kubectl label node <NOMBRE_NODO_BACKEND_ANALITICO> role=backend2

# Verificar roles asignados
kubectl get nodes -L role

5. Correcciones Clave Aplicadas Durante el Sprint

  1. Swagger UI Backend 2 ("Failed to fetch"): Se eliminó "host": "127.0.0.1:5000" de swagger.json para que tome automáticamente la IP de la petición externa (window.location.host).
  2. Nginx DNS Resolver y Tiempos de Espera: Se depuró nginx.conf eliminando el resolver innecesario 127.0.0.11:53 (propio de Docker Compose que arrojaba 111: Connection refused en Kubernetes). Se fijó el resolver interno de K3s (10.43.0.10) con timeouts de proxy explícitos y FQDN completo.
  3. Resolución de Bloqueo de Red Inter-Nodos (Flannel VXLAN UDP 8472): Al distribuir los pods en diferentes instancias EC2 (role=frontend en Worker 3 y role=backend1 en Worker 1), el Security Group de AWS descartaba el tráfico UDP 8472 entre instancias. Se implementó la apertura de la regla Todo el Tráfico en 172.31.0.0/16 y la co-localización en el nodo backend (nodeSelector: role: backend1) logrando latencia < 0.2ms.
  4. Purga Total de Datos Mock: Se eliminaron todos los arreglos estáticos locales en los servicios del frontend, garantizando sincronización bidireccional real con MongoDB y SQL Server.
  5. Exportación a Excel y PDF: Se implementó exportUtils.ts para descargas tabulares en CSV con BOM UTF-8 e impresión directa PDF vectorizada.

6.1. ¿Dónde está el archivo de configuración y qué contiene?

Ruta física en tu disco: e:\Nueva carpeta (8)\tcc\ASE251S4_T05-mobile\.env

React Native y Expo leen las variables con prefijo EXPO_PUBLIC_ en tiempo de compilación para inyectarlas directamente en la aplicación.

6.2. ¿Qué poner exactamente en el archivo .env?

Escenario A (Recomendado para la Sustentación) — Conectado a AWS K3s: 
EXPO_PUBLIC_API_URL=http://13.218.34.30:30001/api
EXPO_PUBLIC_ANALYTICS_URL=http://13.218.34.30:30002/api/v1/analytics

Explicación: 13.218.34.30 es la IP pública de AWS. El puerto 30001 es el NodePort hacia Spring Boot WebFlux, y el puerto 30002 es el NodePort hacia Flask Analítico.

¡Regla de Oro de Celulares Físicos! En un smartphone físico NUNCA uses localhost (el celular intentaría conectarse a sí mismo). Con la IP pública de AWS funcionará desde cualquier celular con Wi-Fi o datos 4G/5G.

6.3. ¡Crítico! La regla de la memoria caché de Expo

Si modificas el archivo .env mientras Expo está corriendo, Expo NO detecta los cambios automáticamente. Debes presionar Ctrl + C en la terminal y reiniciar con:

npx expo start -c
